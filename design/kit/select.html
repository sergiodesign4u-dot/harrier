Atom

Select

One answer out of a short, known set. 4 instances across 1 screen, all of them on the keyboard map, where each row says whether its shortcut is on, needs a modifier, or is off. It is the only component in this system whose keyboard is a file of its own.

Anatomy

Four zones and an order: the control, the value it currently holds, the mark that says there is more under it, and the list. That is why it is a component and not a variant of input: the splitting criterion in the register is anatomy, and until 2026-08-26 this had none, because the platform drew all of it.

That is live. Point at it, open it, walk it with the arrows, type o twice. Nothing on this page is a picture of the component.

<select class="input" id="scope"> <option>On, the letter alone</option> </select> <script src="system/select.js"></script>

The markup is a native select and stays one. The script wraps it, paints a control over it and writes the answer back into it, so a form still submits the element the browser understands and nothing downstream has to know the drawing exists. The class goes on the element, never on a wrapper.

Variants

None. The count of options is a count. Every instance in the product offers three, and a fourth would change nothing here.

When to use it

Use itone answer out of a short set that is known in advance, where the answers are a closed list rather than a search
Do notfor two answers. That is a pair of controls or a switch, and a list of two is a list somebody has to open to learn there was nothing to choose
Do notfor a long list. Past about a dozen the question is a search and the component is a field with suggestions under it, which this system does not have and which goes to backlog.md rather than being bent out of this one
Do notto fire an action. A control that changes the screen the moment it is picked is a menu, and a menu is not this: this holds a value until something else is pressed

Rule and anti-rule

It left input, and the file it left argued against this in writing. The argument is kept rather than deleted, because it is the reason the native control stood for six stages and it is still the reason to be careful here.

What input.css said a drawn select has to reimplement the popup, the keyboard and the screen reader, and gets one of the three right
What changed the owner decided on 2026-08-26 that the platform's popup does not belong inside a console whose whole claim is that it is calibrated. The arrow, the plate, the ink and the type of the open list were the operating system's, and different on every machine a case is opened from
So the price is paid all three are implemented. The popup is in select.css, the keyboard is in design/system/select.js as a real implementation, and the screen reader is served by a combobox that owns a listbox through aria-activedescendant
Never a div with a click handler on it. If the next screen needs a control like this one and reaches for a shortcut, it takes this component or it takes the native element. There is no third thing

Limits

Arrows do not commit while the list is open, moving does not change the answer. This differs from the platform on Windows and agrees with it on macOS, and the reason is the one screen it stands on: a shortcut map is a set of settings, and somebody walking down it with the keyboard must not change four of them on the way past
The options are never focusable focus stays on the control the whole time. Tab therefore leaves, the way it does on the native element, rather than trapping somebody inside a list of three rows
It does not run under the point below --bp-split-panes the control is handed back to the native select. A phone puts a wheel under one that no list of rows can beat, it is reachable one handed, and it never opens off the bottom of a 360 screen
One list at a time a pointer down anywhere outside closes it. There is no rule keeping two open at once because there is nothing that opens a second one while the first has focus

States

Live, in both themes. Point at the control, reach it with Tab, then press Enter.

hoverthe boundary answers and the ground does not move. A field's ground is the page, and a plate under it while the pointer passes would read as it being filled in. --line-hover
focus-visiblethe ring is declared once, in base.css, and this file repeats none of it. It stands outside the boundary at 1px offset and does not replace it
openthe mark turns by the same half turn the disclosure uses, in the same direction, at --dur-fast. The boundary takes the hover line as well, because a control with a list hanging off it is not at rest
the active rowthe pointer and the keyboard land on the same row. There is deliberately no :hover rule on an option: the pointer sets the same class the keyboard sets, so a person moving by keyboard while the pointer rests elsewhere never sees two rows offered at once
the chosen rowground and a tick. A row told apart by its background alone is a row nobody can tell apart in a high contrast mode, where the ground is dropped and the glyph is not
out of reachthe whole control dimmed by --opacity-disabled, never a repaint. The product has zero of these and the system draws it anyway, because a system that cannot show a control out of reach hands the next person a decision to invent
activedoes not exist. The pointer goes down and the list opens, which is a state this file already draws

What it reads, and where it stands

Fill--bg-page on the control, --bg-surface on the list, --bg-selected on the chosen row, --bg-hover on the active one
Ink--text-primary, --text-secondary on the mark, --text-accent on the tick
Line--rule-control on the control, --rule-edge on the list, --line-hover, and --color-focus through base.css
Geometry--radius-ui, --space-1 to --space-3, --opacity-disabled, --dur-fast, --ease-standard, --bp-split-panes
Glyphsexpand for the mark and accept for the tick, both from design/system/icons.js, both applied as masks so they take currentColor. The second copy of each drawing is compared character for character by design/kit/checks/icons.mjs
No shadowand that is not an oversight. There is not one box-shadow in this system. A dialog is told from the screen by a scrim and a toast by its own edge, so a shadow here would be a device the product does not own, introduced for one component with four instances
Stands ondesign/keyboard.html, 4 instances, inside keyrow--set
