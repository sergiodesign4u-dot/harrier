Why this node is not a help screen

WCAG 2.2 SC 2.1.4 Character Key Shortcuts is Level A, and it regulates exactly the interaction this product is built on. Verbatim: "If a keyboard shortcut is implemented in content using only letter (including upper- and lower-case letters), punctuation, number, or symbol characters, then at least one of the following is true", followed by three conditions: turn the shortcut off, remap it to include a non-printable key, or make it active only when the component has focus. Accept, amend and reject on single keys are precisely the case. So this node is the mechanism, not the manual.

01 · Which of the three routes the product takes

Two of them, and the reason is not bureaucratic

The Understanding document is blunt about who single key shortcuts break. They "are disastrous for speech users", because dictation is interpreted as commands, and "keyboard-only users who have dexterity challenges can also be prone to accidentally hitting keys". In a product where one key files a verdict against a client, an accidental keypress is not an annoyance.

The primary route falls out of the split pane the product already has. The list is a grid with its own key handling and the case pane is a separate focus scope, so verdict keys being live only in the case pane is not a bolted on rule, it is the structure. The second route ships anyway, because focus scoping alone still leaves a speech user with no way to stop a meaning accept while the pane is focused, which is the exact scenario the criterion describes.

Inherited by cluster 4, stated here so it is not rediscovered ten nodes later

Every node that binds a single character key declares it in this map and honours the focus rule. A key that fires while a text field has focus is a defect, not a convenience: while 4.5 amend or the 4.4 reason field has focus, letters are text.

02 · The overlay exception

Principle 5 forbids overlays. This is one

The contradiction is real and is resolved rather than ignored. It is allowed because it is the one overlay that carries no decision. It is opened deliberately, it asks nothing, and it leaves on one key. Nothing is lost behind it because nothing behind it is being read at that moment: an analyst opening a shortcut list is not mid sentence in a verdict.

What would break the principle

An overlay that appears on its own
An overlay that asks a question
An overlay over the evidence being judged

What this is

Opened deliberately
Asks nothing
Leaves on one key, inert underneath

And it is not the teaching mechanism. Principle 3 says override is one key and it teaches. Teaching happens at the control: every action with a key shows that key on itself, in place. The map is a lookup for the whole set. If the map is the only place a key is visible, the control has failed and the map is covering for it.

03 · A collision this node found

Escape was already taken

At 0.1, Escape deselects and returns the detail pane to the fleet. The dialog pattern says "Escape: Closes the dialog." Both are right, and together they are a bug.

Resolved, and inherited by every future dialog

While the map is open, Escape closes the map and does not propagate. One press closes it, a second press deselects. Without that rule an analyst dismissing the map silently loses their case selection, which is the kind of loss that gets blamed on the person rather than on the interface. Stated as a product rule rather than a local fix: a modal consumes Escape. 4.4 and 4.6 inherit it.

06 · Dialog behaviour

From the authoring practices, verbatim

RequirementVerbatim
Tab"Moves focus to the next tabbable element inside the dialog. If focus is on the last tabbable element inside the dialog, moves focus to the first tabbable element inside the dialog"
Shift plus TabThe reverse, wrapping to the last
Escape"Closes the dialog"
Focus on open"When a dialog opens, focus moves to an element inside the dialog"
Focus on close"When a dialog closes, focus returns to the element that invoked the dialog"
Outside"Windows under a modal dialog are inert. That is, users cannot interact with content outside an active dialog window"

The invoker is often a key rather than a button. Opened by shortcut, there is no invoking element, so focus returns to whatever held it before. That is the reading the pattern intends when it allows for an invoking element that no longer exists.

  2. Does the focus rule survive the fleet? The pane at rest holds 3.5, not a case. Verdict keys must be inert there, so the focus scope is not "the pane" but "a case in the pane". A distinction with a real bug behind it.
